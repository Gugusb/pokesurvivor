# 挑战镜像采集与运维

本功能只为后续竞技场收集构筑样本，玩法方案见 [ARENA_DESIGN.md](ARENA_DESIGN.md)。本版不开放竞技场或发放积分。

## 生产升级步骤

保持单Node进程和同一个SQLite数据库，**更新前先按 [SELF_HOSTING.md](SELF_HOSTING.md) 在网页根目录之外做SQLite快照备份**。不要清空存档，不把备份放入网站或Git。

1. 获取v0.46.0或之后版本，一并更新网页构建、`mobile-assets.json`和Node源码。
2. 在服务实际目录执行 `npm --prefix server ci --omit=dev`，按现有进程管理方式重启原服务。保持既有 `DB_FILE`、`PUBLIC_ORIGIN`、`TRUST_PROXY` 和端口，启动时自动新建镜像表及索引。无需更改反向代理规则，不开放数据库或新增公网端口。
3. `GET /api/health` 应显示 `mirrorRecorder:1` 和相应新版本。此请求不公开镜像数据。
4. 用独立测试账号正常单人游玩到4分钟，等下一次普通心跳或结束本局；设置→操作的“保留挑战镜像”需开启，不使用F2、不改时钟。源码调试入口不采集。
5. 在服务器用与服务一致的 `DB_FILE` 只读查看统计：

```bash
DB_FILE=/var/lib/pokesurvivor/game.sqlite node server/mirror-status.cjs
```

统计只输出样本数、人数、压缩体积、时间范围、时间桶和构建分布，不展示玩家口令、Cookie、姓名或具体构筑。首批样本可能等待下一次心跳；采集不会额外要求玩家重新登录。

## 请求和存储边界

- 现有 `/api/run/beat`、`/api/run/end` 支持可选 `mirrors` 数组；服务端先处理普通战果，再独立验证可选样本。异常样本返回丢弃确认，不使正常心跳或结算失败。
- 补传端点 `POST /api/mirrors/batch` 需原有同源登录会话、原有客户端请求头。每批最多10份，每账号每分钟20次限制；正常客户端仅在后台约每分钟及恢复网络时尝试，失败不发提示、不进入普通存档重试队列。GET不提供快照读取。
- 返回 `accepted`／`discarded`／`retry` 稳定编号列表。尚未创建或尚未汇报到该时间的对局暂缓；不为采集而修改已知游戏时钟。结束回执丢失可安全重试，遗留队列也可独立补传。
- 每局5份，单份最多32KiB；本机每账号最多30份、7天。服务端gzip保存白名单战斗字段，不保存聊天、口令、Cookie、恢复码、视频或连续鼠标轨迹。
- `mirror_snapshots` 每账号每时间桶保留最近3份，保留35天；全局最多50000份，在接收时按最多每小时一次清理。全局限制是定期软上限，清理周期内可短暂超过；删除逻辑不做`VACUUM`或长事务重写整库。需监控真实样本大小与SQLite文件增长。
- 用户注销会删除本人样本；对局后续标为调试会删除该局样本。封禁／注销账号应在未来匹配查询时排除。当前尚无任何对外匹配读取接口。
- 结构验证不是服务器战斗重演；未来积分和排名不能直接把上传数据当作已验证胜负。

## 停用与回滚

设置环境变量 `MIRROR_RECORDER=0` 并重启：health显示0，不再采样落库，现有普通战果继续接受。已经上传的样本保留，等待后续运维按数据保留规则处理，不擅自清空历史。移除环境变量可恢复。

若需要回退服务版本，保持数据库备份；新增表不修改原存档结构。旧客户端继续工作，新客户端对没有能力标记的旧后端不附带镜像。关闭采集后页面仍可游玩，不应要求玩家清理浏览器缓存来处理采集队列。

APK游戏逻辑由网页更新，无需为了本记录器重新打包安卓壳。网页同时发布新的素材清单，旧APK会继续复用未变化素材。

本次开发和自动化验证只使用本地隔离数据库；实际生产启用状态以目标服务器health和只读统计为准，不能把代码推送当作线上已部署。
